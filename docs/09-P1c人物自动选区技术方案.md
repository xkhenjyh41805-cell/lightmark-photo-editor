# P1c 人物自动选区技术方案

> 复核日期：2026-10-24  
> 状态：**候选方案评估中；尚无模型达到可集成/自动应用验收标准**  
> 产品优先级：人物 → 宠物 → 背景 → 天空（天空先做仅用于验证本地蒙版闭环，不改变产品优先级）

## 1. 目标与约束

本阶段要验证的是：Agent 能否根据用户自然语言和画面上下文，调用本地工具生成**可单独选择的人物实例蒙版**，再对蒙版应用传统、非生成式修图参数。多人场景中，至少要能够区分每个人；用户说“把左边穿红衣的人提亮”时，模型/Agent 必须能将描述绑定到正确实例。语义前景“把所有前景人物连成一片”不能替代逐人选择。

产品约束：

- **非生成式**：不使用生成式重绘或以生成内容替换照片像素；分割模型只产出区域候选，修图由现有传统参数工具完成。
- **本地隐私**：人物分割默认在本机运行，照片像素不上传到云端分割服务。用户配置的多模态 LLM 可能接收预览图用于理解意图，必须遵守应用现有授权与隐私说明；本地模型本身不联网传图。
- **可撤销**：创建蒙版与局部调整应纳入同一可撤销历史事务；用户可检查、修正、拒绝或撤销。模型置信度不能等同于正确性。
- **Agent 边界**：Agent 负责理解描述、选择工具/蒙版并解释原因；低把握或多个候选难以区分时应追问/请求确认，而非静默把不确定蒙版应用到照片。
- **质量判定**：以逐实例区分、目标人物命中、宠物/背景误选、边缘质量、分辨率适配和设备时延共同判断；少量公开图 smoke test 不构成自动应用认证。

天空闭环及现有候选确认、蒙版修正、撤销和隐私边界见[本地自动天空候选蒙版 POC](08-本地自动天空候选蒙版POC.md)。人物不是“把 sky 标签换成 person”即可完成，需要实例分割/对象提示与 Agent 指代消歧。

## 2. 已有隔离实验

测试复用了三张公开样例：COCO 单人滑雪图、多人合照图、猫咪负例。图像约为 640×425/480。以下都是探索性 smoke test，未使用逐像素标注计算 IoU；推理时间受运行时、量化和线程设置影响，只在同机同设置的实验范围内参考。

| MediaPipe Selfie ONNX，CPUExecutionProvider | 模型仅约 0.21 MB、输入 256×256，单人 mask 覆盖约 10.4%，多人输出为约 41.9% 的**联合前景 mask**，不是逐人实例；猫图误分为约 60.6% 人像前景，提高阈值至 0.9 仍约 33.8%。推理约 6–10 ms。 | 速度很快，但语义为 selfie/前景二值分割，不区分独立人物；猫咪负例也不可靠，不可承担人物自动选区。结果见任务 `.work/p1c-benchmark/mediapipe_selfie_results.json`。 |

## 3. 候选路线及部署/许可风险

1. **MediaPipe Selfie Segmentation / Image Segmenter**：Google 官方 Web JS 支持本地图片分割；Selfie 模型面向自拍/人物前景而非每个人独立输出。本机 ONNX smoke test 已确认很快但多人 mask 合并、猫负例误分。适合单人前景或作为某些场景的辅助候选，不满足当前逐人目标。
2. **RTMDet-Ins**：OpenMMLab 实例分割路线，已有预导出 ONNX 可在本机 CPU 运行。实际 POC 证明可提供 COCO person 实例，但多人阈值/小目标仍需有标注的照片集验证；需分别审查实现、checkpoint、转换权重和随附 NOTICE 的许可，不只看代码仓库许可。
3. **YOLO26n-seg**：实例分割接口与类别筛选最接近本阶段需求；当前第三方 ONNX 导出元数据标明原始 Ultralytics YOLO26n-seg、COCO、AGPL-3.0。Ultralytics 官方许可说明闭源/专有软件或商业产品通常需要 Enterprise 许可，除非接受 AGPL 义务。**在 LightMark 产品发行方式及许可适配确认前，仅允许隔离研究，不加入应用依赖、不随安装包分发。**
4. **SlimSAM / EdgeSAM / SAM 2 / SAM 3**：提示式分割可供用户点选目标或作为修正工具，但通常仍需提供点/框/文本提示；不能自动解决“Agent 该选哪一个人”的类别识别与语言指代。EdgeSAM 的模型许可/商用限制、SAM 系列的模型权重和运行资源须逐一核查；SAM 2/3 目前仅作能力上限参考，尚未在目标 Windows 设备完成等同样例的 CPU 评测。
5. **后处理**：置信度过滤、class-wise NMS、mask-overlap 去重只能减少重复候选，不能从无标注测试中确定真实召回率。对小人物提高阈值可能把真正人物删掉。后续可以探索边界细化，但不可用后处理掩盖模型漏检或伪造质量结论。

## 4. YOLO26n-seg 隔离 POC 详情（2026-10-24）

使用第三方发布的 ONNX 转换文件 `zwh20081/yolo26-onnx`，文件 11,218,161 bytes，SHA-256：`7c26e6908a2ded81162e7f40e9b6c783394069bd12d500f0c325afdeb2e644f4`。元数据为 640×640 输入，检测输出 `(1,300,38)` 和 mask prototypes `(1,32,160,160)`，训练来源标为 COCO，作者 Ultralytics、版本 8.4.15、许可 AGPL-3.0。当前 Windows 目标机为 Intel i5-1340P、无 CUDA；POC 采用 Python 3.9.1、ONNX Runtime 1.19.2、CPUExecutionProvider、4 个线程。

|样例|检测与 mask|热态中位数|
|---|---|---:|
|COCO 单人滑雪（640×425）|confidence 0.9447；1 个 NMS 后 person instance；mask 29,350 px / 10.79%|59.12 ms|
|COCO 多人（640×480）|阈值 0.25 下 12 个 person 候选，经 NMS 保留 11 个；mask prototypes 解码为逐实例 mask|53.45 ms|
|猫咪负例（640×480）|0 个 person；cat 类最高 confidence 0.9039|50.96 ms|

图像目视检查：单人 mask 大致覆盖滑雪者；多人图有独立颜色的实例区域，人物大多分开，但必须用标注图确认低置信远处人物、重叠边缘与漏检；猫图没有误成人物。没有计算 ground-truth IoU，也没有高分辨率重采样测试。详情、脚本和可视化保存在任务工作区 `.work/p1c-benchmark/yolo26n_seg_results.json`、`yolo26_seg_smoke.py` 和 `overlays/yolo26n-seg-*.png`；模型权重保存在 `inputs/p1c-benchmark/yolo26n-seg.onnx`，不属于产品依赖。

## 5. 接入门槛与后续步骤

### 必须满足的产品验收

- 多人照片能返回逐人独立候选，且候选 ID 在 Agent 计划与 UI 中稳定对应；不得把语义合并 mask 伪装成逐人选择。
- 有单人、多人、远处小人物、遮挡、侧身/背身、深色衣物、复杂头发边缘、逆光、宠物负例等有授权样片；为代表样片准备人工标注 mask 和目标人描述，分别报告像素 IoU/边界质量、实例漏检/误检、目标指代命中率与运行时间。
- 先定验收阈值，再运行候选比较；不以 confidence 或模型自报的 predicted-IoU 作为真实精度。低置信/描述歧义应让 Agent 澄清或要求用户选人。
- 原图不上传本地分割器；生成的候选蒙版先预览/可修正；Agent 修改走现有安全计划校验、确认策略和撤销栈；禁止生成式重绘。
- 对真实照片测试高分辨率 downscale/upscale、mask 边缘细节、内存、冷启动/缓存耗时、取消行为与失败回滚。
- 许可与权重来源通过审核后才可集成；若最终产品闭源或商业发行且不采用 AGPL，则排除 YOLO26n-seg，并优先找许可兼容候选。

### 下一步顺序

1. 明确 LightMark 未来发行方向（个人自用/开源/闭源商业）与是否可以接受 AGPL；若不能，YOLO26n-seg 仅留作质量/速度对照。
2. 用获得授权的真实照片建立小型但有代表性的本地测试集；用户照片不需要上传给我或第三方服务。若暂时没有，可先扩充带 COCO 实例标注的公开样例。
3. 在同一数据和硬件上比较许可可用的 RTMDet-Ins/替代实例模型与 YOLO；复核面具的逐人边界和阈值曲线。
4. 只有质量、隐私、许可和性能门槛都通过，才做应用内模型下载/缓存、Worker 推理、Agent 工具接口与蒙版审查 UI 的集成；先以“候选 + 用户确认”为默认，不自动静默应用。

## 7. RTMDet-Ins-S：许可兼容候选的标注集评测（2026-10-24）

### 来源与隔离条件

本轮评测使用 `LibreYOLO/LibreRTMDets-seg` 发布的 RTMDet-Ins-S checkpoint，通过 LibreYOLO 1.6.0 在 CPU 上运行；权重 SHA-256 为 `29ffa1d3719d335034259c6e1b2accd68c50460f86a44c9d08f497041ee4153f`。模型仓库标注 Apache-2.0，并注明源自 OpenMMLab MMDetection 的 RTMDet-Ins-S COCO 权重；仓库随附 LICENSE/NOTICE，仍需在产品发行前复核原始权重和派生/转换权重的许可链。依赖、权重与脚本均隔离在任务 `.work/tools`、`inputs` 和 `.work/p1c-benchmark`，没有加入 LightMark 依赖或默认模型目录。

外部模型页报告全 COCO val2017 mask mAP50-95 为 0.3872；这不是本轮子集测得的指标。本轮在同一固定、按场景分层的 50 张 COCO val2017 图像上评测，其中含 205 个非 crowd person 标注；图片从数据集记录的 CC BY 2.0 license id 4 中筛选。输入为 640×640，CPU PyTorch 2.8.0、4 个线程，模型 NMS IoU 0.45。COCO 标注 person 的 category id=1；LibreYOLO 预测类别使用零基索引 class 0，评测代码分别处理两种编号。mask 指标以预测/GT 实例 mask IoU=0.50 和 0.75 做匈牙利匹配；COCO 多边形被栅格化，crowd 标注不计入。

### 结果与比较

|候选及阈值|实例 mask IoU ≥0.50：P / R / F1|实例 mask IoU ≥0.75：P / R / F1|CPU 单张中位数 / P90|
|---|---:|---:|---:|
|RTMDet-Ins-tiny ONNX，0.30|0.671 / 0.698 / 0.684|0.441 / 0.459 / 0.450|1020 / 1662 ms|
|YOLO26n-seg ONNX，0.25|0.862 / 0.580 / 0.694|0.652 / 0.439 / 0.525|513 / 903 ms|
|RTMDet-Ins-S，0.30|0.702 / 0.737 / 0.719|0.488 / 0.512 / 0.500|1252 / 1475 ms|

Tiny 和 YOLO 数据取自本计划前述同一 50 图基准，阈值分别为基准设置 0.30/0.25；不同推理后端和 NMS 实现会影响速度与候选，因此运行时只作同机量级参考，不应视为完全同管线比较。RTMDet-S 在 IoU 0.50 的总体 F1 较 Tiny 高约 3.5 个百分点；在 IoU 0.75 时仍只到 0.500，且总体 F1 略低于 YOLO 的 0.525。RTMDet-S 在 0.40 阈值时 IoU 0.50 P/R/F1 为 0.824/0.615/0.704；0.60 时 precision 升至 0.977，但 recall 降至 0.415。降低到 0.15 虽将 recall 提高到 0.815，F1 仅 0.524，并产生大量误检。阈值调整无法同时解决召回和精度。

### 目视失败案例及结论

人工复核的代表图显示：COCO `000000094751.jpg` 有 11 个标注人物，RTMDet-S 在阈值 0.30 下仅预测 1 个；`000000183246.jpg` 有 2 个标注人物，预测为 0；`000000205289.jpg` 有 1 个标注人物，预测为 2 个。前两例说明远处/小人物和拥挤场景仍有严重漏检，第三例展示实例重复或额外候选。对选取的 8 张无人物动物负例，0.30 阈值未输出人物，但这个小负例数不能证明真实照片中没有误检。

示例对照图在任务工作区 `.work/p1c-benchmark/rtmdet-s-overlays/`；完整指标在 `rtmdet_ins_s_eval.json`，复现脚本为 `scripts/rtmdet_s_eval.py`，权重和来源材料保存在 `inputs/p1c-benchmark/rtmdet-ins-s/`。推理通过 LibreYOLO 的 `load_untrusted_torch_file`，检查确认其使用 PyTorch `weights_only=True` 路径；未启用 pickle 的不安全回退。

**决策：RTMDet-Ins-S 是比 Tiny 有一定召回/F1 改善、且权重许可声明较清楚的隔离候选，但没有达到自动蒙版门槛，不集成 LightMark、不自动应用。** 50 张 COCO 子集不能代表真实摄影作品，也没有覆盖高分辨率边缘和 Agent 文字指代目标。下一步应扩展有人工真值的分层集合（重点为小人物、拥挤/遮挡、宠物负例和复杂边缘），再以用户授权、无需上传的本机真实照片检查高分辨率复原、耗时及选人命中率；若仍不达标，继续保留人物自动选区关闭状态。

模型来源：[LibreYOLO RTMDet 文档](https://www.libreyolo.com/docs/models/rtmdet)、[RTMDet-Ins-S 模型卡](https://huggingface.co/LibreYOLO/LibreRTMDets-seg)、[模型文件及 LICENSE/NOTICE](https://huggingface.co/LibreYOLO/LibreRTMDets-seg/tree/main)、[LibreYOLO 安装/运行时要求](https://www.libreyolo.com/docs/install)。


## 8. 200 图分层基准复评（2026-10-25）

### 数据与方法

在固定的 COCO val2017 子集上完成三模型复评：200 张唯一图片、796 个非 crowd person 实例标注，图像均筛自记录许可为 id 4 / CC BY 2.0 的样本。分层互斥：单人 40 张、2–4 人 40 张、5+ 人 40 张、含至少一个小人物 40 张、无人物猫狗负例 30 张、其他无人物负例 10 张。小人物分层依据 COCO GT `area < 32×32`，不应解读为物理尺寸或产品阈值。

三个模型分别使用固定置信阈值：RTMDet-Ins-tiny 0.30、YOLO26n-seg 0.25、RTMDet-Ins-S 0.30；实例 mask 以 IoU ≥0.50 / 0.75 进行匈牙利匹配，报告实例级微平均 P/R/F1。标注多边形栅格化、crowd 标注排除。评测在 Intel i5-1340P Windows CPU 环境运行；RTMDet-S 使用隔离的 LibreYOLO/PyTorch CPU 环境，Tiny 与 YOLO 使用 ONNX Runtime CPU。不同预处理、运行库与 NMS 管线意味着推理时延只能作量级参考，不是严格同管线竞速。

### 总体结果

### 评测结论与决策

RTMDet-Ins-S 在 IoU 0.50 总体 F1 最高（0.719），并在单人、2–4 人、5+ 人和小人物层都取得最高或并列较高的 F1；其小人物召回率 0.664，高于 Tiny 的 0.608 和 YOLO 的 0.507。拥挤 5+ 人层的召回率为 0.744，但 precision 只有 0.662、产生 135 个 FP，不能只按召回率选型。严格 IoU 0.75 时 YOLO 总体 F1 最高（0.487）；RTMDet-S 为 0.458，小人物边缘严格匹配 F1 仅 0.369。RTMDet-S 的 CPU 单张中位数约 1.27 秒，明显慢于 ONNX 候选。

**结论仍为不集成、不自动应用。** 200 图使相对趋势比 50 图初测更稳定，但仍是 COCO 分层子集；没有检验真实高分辨率原图上的边缘复原、复杂遮挡、Agent 自然语言指代命中率或用户主观可用性。RTMDet-S 仓库的 Apache-2.0 声明值得继续核查，但原始权重及转换权重的许可链仍需产品发行前复核；YOLO26n-seg 仍受 AGPL-3.0 风险约束，只保留隔离研究对照。下一步仍需在用户授权、留在本机的真实照片上做标注/选人验证，保持候选预览、可修正、确认和撤销，不允许低质量蒙版静默应用。
