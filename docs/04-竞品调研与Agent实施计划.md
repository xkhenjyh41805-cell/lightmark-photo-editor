## 一、结论先行

LightMark 已有最难从零搭起的修图基础：全局调整、HSL、渐变／径向／笔刷蒙版、预设、历史撤销、裁剪旋转、非破坏 sidecar 和导出。当前代码已把现有调整工具连接到**受限、可验证、能回滚的 Agent 工具箱**，并接入通用 OpenAI 兼容视觉模型接口。下一步不是再写一套聊天框，而是由用户在应用设置里配置自己的 Qwen 或 DeepSeek API Key，完成真实图文联调和桌面验收。

调研确认了一个关键产品边界：**用户通过对话表达目标；多模态 Agent 理解“要改什么、改哪里”，调用传统工具主动修图，并另行提出可采纳建议；分割工具负责生成像素区域；用户负责审阅、追问和决定。**参考图风格也应先转成可检查的参数配方，再应用于目标照片，不做图生图或内容替换。

建议的顺序：

1. ✅ 完成单张照片 Agent 核心：受限输出、白名单工具、事务式撤销。
2. ✅ 完成用户自带多模态模型的 OpenAI 兼容接入代码；真实服务商调用待用户配置密钥实测。
3. ✅ 将 Agent 侧栏接入实际桌面应用；待真实模型下验收主动修闭环。
4. 单独验证语义蒙版；质量不达标就保留手动蒙版，不阻塞 MVP。
5. 单图稳定后先做手机伴随版可行性 POC，再按反馈决定批次工作区和配方的实施顺序；完整移动修图不纳入首个手机版本。**批量导出已经存在，不等于 Agent 已能安全批量修图。**

## 二、对照其他修图软件：值得学什么

以下只借鉴公开文档中的工作流和交互，不代表 LightMark 已集成这些能力，也不意味着其专有代码、模型或素材可复用。

### Adobe Lightroom / Lightroom Classic

- **值得借鉴：**照片筛选、评级／旗标、网格与并排比较、非破坏编辑；局部蒙版能显示叠加层并用添加／扣除等方式细修；批量同步时可选择要复制的调整类别。
- **对 LightMark 的启发：**建议的作用范围必须看得见；批量操作要让用户选目标照片和同步项；自动蒙版跨照片时应重新计算并逐图检查，而不是复制第一张的像素坐标。
- **注意：**Lightroom Classic 与云端 Lightroom 的资产模型不同；商业软件的工作流可参考，但不能当作 LightMark 的 SDK 或算法来源。
- 资料：[Masking tool（Classic）](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/masking.html)、[Library 模块筛选与比较](https://helpx.adobe.com/lightroom-classic/desktop/help/library-module-basic-workflow.html)、[批量编辑](https://www.adobe.com/products/photoshop-lightroom/batch-edit.html)。

### Capture One Pro

- **值得借鉴：**Cull 工作流可评级、筛选和比较相似照片；图层／蒙版将局部范围与调整明确关联；多图编辑要求用户先选择照片和设置同步范围。
- **对 LightMark 的启发：**未来批次应分清“筛选目标照片”和“应用哪些编辑”，并显示主图、目标集合和例外；专业用户需要能查看蒙版与参数。
- **注意：**并非所有滑杆都自动作用于全部选中图片；其 AI Masking 和产品许可不代表可直接集成到 LightMark。
- 资料：[Culling images](https://support.captureone.com/hc/en-us/articles/7185822431645-Culling-images)、[图层与蒙版](https://support.captureone.com/hc/en-us/articles/360002601658-Overview-of-Layers-and-Masks)、[多图调整](https://support.captureone.com/hc/en-us/articles/360002480877-Adjusting-multiple-images-at-a-time)。

### DxO PhotoLab

- **值得借鉴：**图库、全局调色和局部调整分区清楚；蒙版可命名、排序、组合、反相并与局部参数关联；多选时可以选择复制全部、全局或局部调整。
- **对 LightMark 的启发：**蒙版应作为有状态、可编辑的对象，而不是模型临时返回的一张黑白图；复制局部调整时要重新评估区域是否适用于另一张照片。
- **注意：**DxO 的自动选择是其集成能力和硬件／版本条件的一部分，并无据此可确认的通用嵌入 API。
- 资料：[局部调整与蒙版](https://userguides.dxo.com/photolab/en/local-adjustments/)、[批量与菜单功能](https://userguides.dxo.com/photolab/en/menus-preferences-and-functions/)、[离线与联网说明](https://support.dxo.com/hc/en-us/articles/6887830503453-Does-DxO-PhotoLab-require-internet-access)。

### Luminar Neo

- **值得借鉴：**浏览与编辑上下文衔接、编辑历史可见、批量同步后检查结果；局部蒙版可以手工细化。
- **对 LightMark 的启发：**爱好者可先收到少量主动建议，专业用户仍可展开参数和调整清单；多图同步应显示不可同步项目及结果检查入口。
- **注意：**产品同时含生成式擦除、替换等功能；LightMark 应只参考传统调整、局部遮罩和非破坏工作流，不能把“AI 修图”混为同一种能力。
- 资料：[蒙版选项](https://support.skylum.com/editing-tools/masking-options)、[同步调整](https://support.skylum.com/how-to-use-luminar-for-desktop/catalog/syncing-adjustments)、[非破坏式目录编辑](https://support.skylum.com/how-to-use-luminar-for-desktop/catalog/catalog-files/catalog-database)。

### ON1 Photo RAW

- **值得借鉴：**图库筛选、评级、相册／智能相册、单图和批量预设；局部效果和遮罩与非破坏编辑结合。
- **对 LightMark 的启发：**单张编辑稳定后，批次可采用“筛选—选参考照片—选择要同步的参数—逐图检查”的渐进流程。
- **注意：**ON1 2027 的部分 culling／监控文件夹等是官网预告，不作为已交付能力或 LightMark 首版依据；产品也混有生成式和云端 AI 功能。
- 资料：[Photo RAW 2026 用户指南](https://on1.clickhelp.co/resources/Storage/photo-raw-2026-user-guide.pdf)、[功能说明](https://www.on1.com/products/photo-raw/features/)、[版本预告](https://www.on1.com/products/photo-raw/whats-new/)。

### 像素蛋糕

- **值得借鉴：**更贴近商业摄影工作流：图库状态、星级／旗标／色标、多条件筛选、单图精修与按功能勾选的批量同步。
- **对 LightMark 的启发：**粗筛、精修、交付可以分成不同任务阶段；批量动作先选图片、再勾选调整类别，提示目标张数并显示进度。
- **注意：**它面向影楼和商业人像，包含生成式创意及云端能力；公开资料未显示可嵌入 LightMark 的 SDK。其功能只能作为交互参考，不证明其内部算法或云端数据路径适用于 LightMark。
- 资料：[桌面工作区介绍](https://www.pixcakeai.com/guide/32445)、[项目图片筛选](https://www.pixcakeai.com/guide/32447)、[批量应用效果](https://wiki.pixcakeai.com/guide/9591.html)、[创意模块说明](https://www.pixcakeai.com/guide/127932)。

### 共同规律

成熟软件都把“选片、调整、审阅、导出”分开；局部调整通常要求可见蒙版；批量编辑会显示目标和设置范围。LightMark 可以从聊天式交互起步，但不能把聊天当作工作区本身。主动修之后，用户仍应能看到**改了什么、作用于哪里、如何撤销**。

## 三、可供后续验证的图像工具／开源项目

### 单张语义蒙版：优先做小型 POC

- **SAM 2：**适合点选／框选后产生分割候选，并可继续用提示细化；它不理解“天空”这类文字语义，本身也不做修图。可先作为交互式蒙版基线。[官方仓库与安装说明](https://github.com/facebookresearch/sam2)、[图像预测器接口](https://github.com/facebookresearch/sam2/blob/main/sam2/sam2_image_predictor.py)。
- **Grounding DINO + SAM 2（Grounded SAM 2）：**前者按文字提示产生候选框，后者把框转成像素蒙版；是“理解目标—生成区域”的更匹配路线，但两段都会出错，且 Python/PyTorch/CUDA 集成较重。[Grounded SAM 2 官方仓库](https://github.com/IDEA-Research/Grounded-SAM-2)、[Grounding DINO 官方仓库](https://github.com/IDEA-Research/GroundingDINO)。
- **Florence-2：**可研究描述、OCR、区域定位和多边形类输出；多边形不等于头发等细节的高质量软蒙版，需要光栅化与边缘评估。加载示例使用 `trust_remote_code=True`，需锁定可信模型版本并审查代码。[Microsoft 模型卡](https://huggingface.co/microsoft/Florence-2-base)、[processor 源码](https://huggingface.co/microsoft/Florence-2-base/raw/main/processing_florence2.py)。

**建议路线：**先比较“手工点／框 + SAM 2”与“文字定位 + Grounded SAM 2”；Florence-2 作为备选，不要同时把所有模型塞进首版。语义蒙版需显示叠加层、允许拒绝／细修；未达到质量门槛时走现有笔刷／渐变／径向蒙版。

### 未来批次筛选与照片整理

- **ImageHash：**适合近重复候选，可做连拍或重复图片初筛；不理解场景语义，也不应自动删片。[官方仓库](https://github.com/JohannesBuchner/imagehash)。
- **OpenCLIP：**图像／文本 embedding 可探索自然语言照片搜索或语义候选分组；全图向量不能产生区域蒙版，也不能决定曝光参数。不同权重的许可和语言能力不同；特别是 OpenAI CLIP 模型卡对部署用途有明确限制，不能把代码许可等同于权重可商用。[OpenCLIP 项目](https://github.com/mlfoundations/open_clip)、[CLIP 模型卡](https://github.com/openai/CLIP/blob/main/model-card.md)。
- **ExifTool：**未来可读取相机、镜头、拍摄时间等元数据，辅助筛选与批次组织；它不做画面理解或像素编辑。若写入元数据，要预览、备份、逐格式校验并回读确认。[官方应用文档](https://exiftool.org/exiftool_pod.html)、[FAQ](https://exiftool.org/faq.html)。

### 传统图像处理

- **OpenCV：**可评估滤波、颜色／几何变换、直方图和传统掩码后处理；GrabCut、watershed 属于依赖框或标记的分割，不等同于“自动找主体”的语义分割。它也不是完整 RAW 照片编辑管线。[图像处理模块](https://docs.opencv.org/4.12.0/d7/dbd/group__imgproc.html)、[分割模块](https://docs.opencv.org/4.12.0/d3/d47/group__imgproc__segmentation.html)。

### 集成和许可提醒

SAM 2、Grounding DINO、Florence-2、OpenCLIP、ImageHash 等不能因为开源就假设可直接打进 Electron。模型代码、模型权重、训练数据、第三方依赖、CUDA 构建和云 API 条款需分别审查；先固定版本，在独立 worker／sidecar 中验证。尤其不要让模型或第三方工具获得覆写原图、调用任意命令或自主导出的权限。

## 四、调研后补充的产品需求

本轮可供你评审的新增／补强项另见[新增需求评审清单](./05-新增需求评审清单.md)。批次筛片痛点、同类产品流程和图层建议详见[批次筛选与图层专项调研](./06-批次筛选与图层专项调研.md)。以下按优先级列出研究建议；除你已明确的 Agent 对话方向和本轮直接确认项外，后续能力暂不视为已批准进入首版。

### P0：Agent MVP 必须具备

- **强约束的输出协议：**模型只能输出版本化 `EditPlan`，由应用校验 schema、工具名、参数范围和操作对象。拒绝脚本、路径、任意像素内容、未知工具和越界参数。
- **建议与执行分离：**模型提出的主动建议须说明观察到的现象、影响区域及修改理由，并等用户确认后执行；只有用户明确提出的安全调整可在校验后直接应用。确定性执行器操作现有图像管线；单次 Agent 修改是一笔可追踪事务，可整体撤销，失败时回到执行前状态。
- **数据流可见：**显示当前 provider／model、图像是否离开本机、传送的是缩放预览还是原片、是否包含 EXIF 等；默认去掉与理解无关的敏感元数据。API Key 由主进程安全保管，不进 renderer bundle、日志或普通配置文件。
- **主动修侧栏真实闭环：**提交指令后显示分析、执行、完成或失败状态；结果列出具体参数、理由和作用范围，可继续手调、前后对比、撤销。不能连接模型时明确说明，并允许继续手动编辑。
- **对话与建议分层：**照片切换不新建独立对话；对话接近上下文上限时自动压缩，保留当前照片、关键编辑和未决事项。Agent 的建议需说明现象与理由，用户确认前不执行；不要求隐藏或无限期的长期记忆。
- **不伪装模型能力：**本地规则建议可继续存在，但标明“规则建议”；没有连接多模态模型时不能把规则引擎包装成看图 Agent。
- **原片和导出安全：**模型不得导出、覆盖、移动照片；导出仍由用户主动操作。失败、超时、无效输出不得留下部分应用状态。

### P1：验证后再产品化

- **单张语义蒙版：**Agent 自动整理可命名区域并把“人物／宠物／背景／天空”等自然语言目标绑定到真实 mask ID；首批验证顺序为人物→宠物→背景→天空。清晰无歧义时可直接用于局部传统调整并显示区域；有歧义时追问。支持切换、手动补／擦与撤销，不要求每次都重复确认。
- **非破坏式调整栈：**把全局参数、局部蒙版及 Agent 操作组织为可见、可比较、可微调和可撤销的调整项；不是完整 Photoshop 像素层或混合模式系统。
- **专业展开：**先保持爱好者默认界面简单，再逐步开放详细参数、蒙版来源、区域修整和操作清单；建议模式／主动修模式留作后续交互选择，不拆成两套工具系统。

### P2：单图稳定后

- **批次筛选工作区：**优先解决连拍／近重复比较、最佳候选建议、清晰度／曝光／闭眼提示和状态追踪；摄影师确认保留集。默认不自动删除、移动或导出照片。
- **独立选择与编辑状态：**将 Pick／Reject／最佳候选与未修／处理中／已修／待复核／已交付分别记录，星级和颜色标签不能隐式代替编辑进度。
- **批次配方：**保存用户确认过的操作序列、适用参数和范围；应用前预览会影响哪些照片／设置。
- **内部 Skills：**例如读取允许的照片上下文、生成建议、生成蒙版候选、执行受限调整、检查失败项。Skills 是内部能力，不是让用户看到的“批量模式”替代品。
- **移动端 POC：**桌面单图 Agent 稳定后，先验证手机伴随版的选图、快速筛选、全局参数建议和本机导出；是否发展为完整移动修图器、是否与桌面同步，需由原型和真实使用反馈决定。
- **参考图风格匹配：**用户选择参考图与目标图；Agent 将参考图的影调／色彩特征映射为现有参数可表达的 `StyleRecipe`，提供匹配强度、预览和微调。该功能不搬运像素或内容，需跨场景评估，列为 P2 候选。

## 五、建议采用的三层批次设计

### 工作区（用户可见）

代表一次拍摄或一组待处理照片。显示照片引用、当前选集、筛选条件、分组、处理状态、异常和导出状态。工作区不应未经确认移动原始照片。

### 配方（用户可见、可复用）

保存已确认的参数操作，例如“基础曝光和白平衡统一 + 组内单张微调”。配方要能预览、版本化、复制和撤销；不得保存密钥，也不要把未经验证的自然语言回答或像素蒙版当作确定性事实。

### Skills（Agent 内部能力）

按受限输入输出调用：照片上下文、规则检查、模型建议、候选蒙版、参数执行、预览与异常报告。编排器负责权限、校验、审计与回滚；单个 Skill 不直接改原图或导出。

## 六、具体实施计划与当前执行状态

现有代码基础见 [02-详细方案计划表](./02-详细方案计划表.md)：全局调整、HSL、手工蒙版、预设、历史撤销、裁切旋转及单张／批量导出都已完成。阶段 0–3 的安全工具、通用 Provider 和 Agent 侧栏代码已落地；下表保留设计与验收目标，当前正在等待用户配置服务商凭据并进行真实调用测试。没有在本机或文档中配置用户 API Key。

### 阶段 0：冻结安全边界与数据契约（✅ 已完成代码与自动化验收）

**任务**

1. 盘点当前 `AdjustParams`、HSL、sidecar、历史记录、蒙版 ID／数据和 IPC 接口，确认哪些字段可安全供模型调用。
2. 定义版本化 `EditPlan`：仅含摘要、受限步骤、允许参数及原因；应用端不信任模型输出。
3. 定义工具注册表：MVP 先启用全局参数和 HSL；只读的直方图检查可作为上下文。局部调整须引用真实的 mask ID；验证语义解析器如何把“背景／人物”等自然语言目标绑定到具名蒙版，歧义时追问。
4. 给每次 Agent 修改建立事务边界：保存执行前快照；成功后可一次撤销；任一步失败则回滚整笔操作。
5. 建立 20 条固定指令和负向用例：正常全局修图、模糊指令、局部请求、生成式要求、错误 JSON、越界参数、未知工具、无图／服务超时。

**验收**

- 未知字段／工具、自由代码、文件路径、越界参数和未经确认的蒙版全部被阻断。
- 无效计划不会改变照片状态；已应用计划能一键完全撤销／重做。
- 原图仍只读；sidecar 旧格式仍可加载。

### 阶段 1：先做真实工具执行闭环（✅ 固定计划闭环已完成）

**任务**

1. 不接外部模型，先用固定合法 EditPlan 经过真实校验器，调用现有曝光、对比度、影调、白平衡、饱和度／HSL 参数。
2. 把一组 Agent 操作提交为同一事务；人工滑杆后续变化仍与 Agent 修改分开记录。
3. 对“背景暗一点”这类局部请求，如果无有效蒙版就返回“需要选区”，不能把它误当作全图曝光调整。
4. 更新 `docs/02` 对应状态和回归测试，不删除当前本地规则建议。

**验收**

- 每个支持操作都映射到现有图像管线；预览和全分辨率导出使用同一组已确认参数。
- 20 条固定指令能复现预期的工具选择；所有非法／不支持的指令均不执行。
- 用户可看到逐项变更、修改参数、前后对比、撤销整组 Agent 结果。

### 阶段 2：接入用户自带多模态模型（✅ 通用接口代码已完成；待真实凭据联调）

**任务**

1. ✅ Provider 采用可配置 Base URL 的 OpenAI Chat Completions 兼容接口，预设 Qwen `qwen3-vl-plus`、DeepSeek `deepseek-flash`，并支持自定义端点；不承诺所有兼容服务的视觉或 JSON 能力都相同。
2. ✅ API 请求由 Electron 主进程完成；API Key 使用系统安全存储、绑定 Base URL，renderer 仅能写入密钥和读取脱敏状态。
3. ✅ 设置中提供图文连接测试；首次传图前说明目标、缩小预览与上下文内容，可仅允许一次或记住该 Base URL＋模型授权；请求由用户逐次点击发起，授权可撤销。
4. ✅ 默认只传最长边不超过 1600px 的当前画布 JPEG 预览，不发原始高分辨率文件或 sidecar；API Key 仅作为所选 Base URL 的认证头。
5. ✅ 模型输出解析为受限 EditPlan 并经统一校验；不提供 shell、文件系统或导出工具。真实服务商的视觉输入、结构化输出、错误和实际费用仍需用用户自己的密钥验证。

**验收**

- 配置缺失、密钥错误、不支持视觉输入、超时、限流、无效 JSON 均有明确错误与手动编辑回退。
- API Key 不出现在普通配置文件、renderer、日志和错误提示中。
- 用户能看见何时将照片发给所选端点；关闭或撤销授权后不发送图像，记住的状态可查、可改。
- 至少 20 条指令完成真实模型回归，记录工具选择正确率、参数修改比例、无效输出率、延迟和失败原因；模型建议的审美好坏与安全执行分别统计。

### 阶段 3：把原型体验落到实际工作台（✅ 代码已接入；待人工实测）

**任务**

1. ✅ 将 Agent 侧栏接入当前实际画布和图库，而非只更新静态 HTML 原型。
2. 状态明确区分：未连接模型、等待指令、分析图像、校验计划、正在处理、已完成（可撤销）、需要区域确认、失败。
3. 完成摘要、具体参数、观察现象／修改理由、前后对比、修改强度、调整栈中的独立 Agent 编辑项和整组撤销；将用户明确请求与 Agent 主动建议分开，后者须经用户确认。
4. 保留手动滑杆、预设、局部工具和规则建议入口；清楚区分规则建议与模型建议。
5. 模式选择（主动修／建议模式）作为后续改动，不阻塞首版主动修验证。

**验收**

- 首次使用者能在侧栏完成“输入目标—看到效果—知道修改项—撤销或继续微调”的闭环。
- 模型不可用不影响原有修图功能；加载、失败或取消不会锁住画布。

### 阶段 4：语义蒙版技术验证，不预设必做（4–8 个开发会话）

**候选路线**

1. 基线：现有手工笔刷／渐变／径向蒙版 + SAM 2 点／框提示。
2. 文字语义候选：Grounding DINO 输出框，再给 SAM 2 生成像素蒙版；这是更贴近“选背景／主体”的开源路线，但需要验证 Windows 打包、Python/PyTorch/CUDA 与设备资源。
3. 备选：Florence-2 多边形结果，评估光栅化及边缘质量；不把模型卡或论文基准直接当作照片蒙版质量保证。

**验证集与指标**

- 至少 50 张有代表性的照片，覆盖人物／动物毛发、主体与背景颜色接近、遮挡、多个相似对象、透明或反光边缘、天空／植物等场景。
- 对核心类别制作少量人工参考区域；记录候选命中率、用户评为“可用／需修／不可用”的比例、边缘修正耗时、每张延迟、峰值内存、失败恢复，以及本地／云端数据流。
- 先按人物→宠物→背景→天空建立离线基线，记录正确目标命中、误选／漏选、歧义追问、边缘修整时间、延迟和内存；用真实使用风险与用户可接受度制定内部放行标准，不预设一个固定产品数值门槛，也不把模型分数当准确率。

**产品化验收**

- Agent 能把自然语言目标映射到真实命名蒙版；清晰目标可直接局部处理并显示区域，歧义目标必须追问；蒙版可替换、手工细修和撤销。
- 位置、尺寸、方向、空掩码、版本不匹配等异常均先校验；模型分数不得冒充绝对置信度。
- 未过质量门槛则不进入首版；手动蒙版仍可完成全部局部修图。

### 阶段 5：移动端可行性与伴随版 POC（4–6 个开发会话）

**建议的首期范围**

1. 先做手机伴随版，而不是桌面功能的全量移植：从系统照片选择器选图，快速浏览／评分／筛选，调用同一套受限 Agent 协议提出全局参数建议，提供预览、撤销和导出新副本。
2. 暂不承诺专业级局部蒙版、完整 HSL／裁剪工作台、批次同步、RAW 全格式支持或桌面图库实时同步；依据 POC 和用户访谈再决定。
3. 原片处理、缩略图和模型数据发送路径要分别说明；云端模型调用继续使用明确授权。手机端模型凭据保存在该设备的安全存储中，不默认与桌面同步。

**架构准备与技术选择**

1. 先抽离或明确平台无关的 TypeScript 核心：EditPlan/schema、参数边界、工具协议、配方／操作记录和纯算法；不要现在就为了移动端重写桌面 UI。
2. 用接口隔离平台能力：`PhotoAssetRef`（文件路径／系统照片 URI）、照片选择与读取、预览渲染、凭据安全存储、持久化、导出、后台任务与权限提示。桌面可保留 Electron IPC／Canvas／Sharp 实现，移动端另写原生适配器。
3. POC 时比较 React Native／Expo 等原生客户端与响应式 Web/PWA：若需要稳定访问系统相册、设备安全存储、离线编辑和本机导出，优先验证原生客户端；若只验证选图与远端建议，PWA 可作快速原型。React/TypeScript 业务逻辑有机会复用，但 Electron 的 DOM 组件、Canvas、Sharp 和 Windows 文件路径不能假定可直接复用。
4. 不在本阶段决定云同步方案。先让手机独立读取系统选中的照片并保存本机派生结果；之后若要手机与桌面共享项目，再单独设计局域网传输或云同步、冲突处理、照片存储和数据删除策略。

**验收**

- 在目标手机上能通过系统选图打开照片，得到缩放预览，向已连接的多模态模型发出授权请求，应用一项安全的全局参数建议，并预览／撤销／导出为新文件。
- 编辑记录可在应用被系统挂起或重启后恢复；网络失败、存储权限拒绝、照片 URI 失效时不会丢失原图或卡死。
- 触屏、竖屏布局、低内存和高分辨率照片至少完成一轮设备实测；记录启动时间、内存、推理延迟和导出耗时，再决定是否进入产品化。
- 伴随版能满足目标使用场景后再扩充功能；若必须先依赖未确定的云端照片同步、需要重做整个图像引擎，或无法安全处理模型凭据，则暂停移动端发布并先完善架构。

### 后续候选：参考图风格匹配 POC（待评审，不纳入当前必做排期）

1. 用户明确选择“参考图”和“要修的目标图”；模型只分析曝光层次、对比度、色温／色调、饱和度和当前已支持的 HSL 等可参数化属性。
2. 将分析结果映射为受限、可编辑的 `StyleRecipe`，只调用 LightMark 现有传统工具；不能映射的效果要解释限制，不生成替代图像。
3. 先预览，再提供匹配强度、逐项调整、接受／拒绝、撤销和另存为预设；目标图原片保持不变。
4. 用不同场景的参考图／目标图组合评测风格一致性、场景内容误迁移、建议改动幅度和用户可控性。若模型把参考图中的主体／背景内容误当风格，或不能稳定映射到现有参数，则暂不产品化。

### 阶段 6：试做批次工作区与配方（6–10 个开发会话）

**推荐批次顺序**

1. 选一组照片进入批次工作区；先用时间邻近与视觉相似度建立可编辑近重复／连拍组，支持拆分、合并、忽略和指定参考帧。
2. 提供双图 Compare、多图 Survey、同步缩放和键盘选片；Agent 可标出组内“最佳候选”，但用户可换选、保留多张或拒绝建议。
3. 把模糊／焦点、眼睛状态、曝光异常、近重复作为可解释的提示，不直接删片或最终定稿；闭眼要逐人显示。合照标明疑似闭眼人数，不能因单人闭眼默认淘汰整张；关键人物和聚合规则由用户设置。
4. 分开保存选择状态与修图状态：未审／复核中／候选／Pick／Reject 与未修／处理中／已修／需复核／已交付分别筛选；组内最佳候选独立记录。
5. 首版批次编辑建议先做用户确认选集上的统一全局参数配方，并可预览、微调、撤销；逐图白平衡／曝光归一作为可选实验，显示每张变化并把离群图交给人工复核。
6. 局部蒙版不能复制参考图像素坐标；每张目标图重新识别并绑定具名区域，报告失败／漂移和歧义，供人工处理。
7. 队列支持暂停、继续、取消、跳过单张、失败重试和逐张回滚；单张失败不影响整批。默认不自动删除、移动或导出原片；导出由用户主动启动。

**验收**

- 用户始终知道批次目标张数、配方版本、修改项、筛片理由、最佳候选和每张的选择／编辑状态。
- 单张失败不影响整批；任务可暂停、续跑、取消；可跳过和逐张撤销。
- 每张照片的局部操作都绑定到真实、可见的区域；清晰无歧义时可执行，区域冲突时需澄清／用户选择。批次不自动导出、删除、移动或覆盖照片。

## 七、数据结构与模块边界建议

- `VisionProvider`：发出用户授权的图像理解请求，产出受限结构化建议。
- `EditPlan`：只记录模型建议的合法操作，不携带可执行脚本或原始像素。
- `ToolRegistry`：绑定到现有图像管线，执行前再做白名单和范围检查。
- `MaskProvider`：与大模型 Provider 分离；输入目标／点／框和图像，输出候选区域。
- `Region`：统一保存原图 ID、方向／坐标系、尺寸、类别、box／polygon／mask 引用、生成来源与版本、当前确认状态。
- `EditTransaction`：将一轮 Agent 修改与用户手动操作区分，连接历史记录并支持整组回滚。
- `AdjustmentStack`／`AdjustmentNode`：保存全局参数、局部蒙版、来源、作用区域、显隐与历史关系；作为可读的非破坏式调整项，不引入任意像素混合模式。
- `BatchWorkspace`／`Recipe`：单图稳定后加入；配方只引用确认操作，不保存密钥或原图。
- `PlatformAdapters`：用平台接口隔离照片引用、文件／相册权限、图像渲染、凭据保险箱、持久化、导出和后台任务；共享协议与纯业务逻辑，不共享假定桌面 DOM 的视图。

模型与算法执行建议放在主进程受控 IPC 或隔离 worker／sidecar，不阻塞 renderer。使用 Python/CUDA sidecar 之前，先在目标 Windows 设备实测启动、安装、GPU／CPU fallback、取消与卸载；不要把其可运行性当作现成事实。

## 八、项目风险与暂缓清单

- **不得越界成生成式修图：**首版不做生成式擦除／填补、换天空、换景、扩图、内容替换。即使工具库包含修复或无缝克隆，也须按产品定义排除。
- **不得误用蒙版：**文字定位框不是精细 mask；相似度、置信分数或论文指标也不是编辑正确率保证。
- **不得忽视 RAW／色彩管理：**现有项目使用 Canvas／Sharp 路线，不应仅凭竞品说明就宣称完整 RAW 显影、ICC 管理或专业打印支持；应单列格式和输出质量评测。
- **不得把代码许可等同于模型许可：**开源项目、各模型权重、训练数据、依赖和云端 API 的许可边界不同；对准备打包分发的依赖单独审查。
- **移动端复用边界：**React／TypeScript 不代表 Electron UI 可直接运行在手机上。系统相册 URI、应用沙盒、手机凭据存储、内存／电量限制、照片导出和后台任务都要用独立适配器验证；未决定存储同步前，不要将桌面绝对路径当作跨设备照片 ID。
- **首版暂不做：**跨照片自动认定同一主体、自动删片、自动批量蒙版应用、云端图库同步、监控文件夹、任意工具调用、自动导出、Photoshop 自动化。

## 九、实施前仍需确定的选择

这些选择不阻碍先做模型前安全工具闭环；进入真实模型开发前需定下来：

1. **首个 BYOM 接口：**选一个官方厂商原生 API，还是先做一个已验证的 OpenAI 兼容接口；不能只凭“兼容”标签保证图像输入一致。
2. **传图授权：**已明确首次云端传图前询问，并可选择“记住选择／不再询问”；继续确定记住授权的撤销入口、默认预览尺寸、EXIF 清理和错误重试策略。
3. **蒙版部署：**优先本地模型以保护照片，还是允许用户配置远端视觉服务；本地质量和安装资源需 POC 决定。
4. **首个批次编辑范围：**调研建议先做确认选集上的统一全局参数配方；是否同时试验逐图白平衡／曝光归一仍待决定。筛片提示只作建议，保留集由摄影者确认，且默认不自动删除、移动或导出。
5. **RAW 与支持格式：**盘点当前实际可读取、预览与导出的格式，先承诺项目已验证的能力。
6. **移动端首期形态：**做轻量手机伴随版，还是完整独立修图器？若做伴随版，是否需要桌面同步？建议先验证本机选图、全局主动修和导出，再决定全量编辑与同步。
7. **参考图风格范围：**先只匹配全局色调／色彩，还是还要覆盖局部蒙版？建议首轮 POC 限定为现有全局参数与 HSL，且只生成可审阅的参数配方。

## 十、总体建议

**模型前的安全工具闭环已完成首轮实现。**现有代码新增版本化 EditPlan v1 校验，仅允许全局参数与 HSL 白名单工具；校验未知字段、非有限数和越界参数；主动建议在确认前不会生成可执行状态；应用端把候选状态写入当前 PhotoAdjust，并以 compare-and-swap 阻止过期计划覆盖较新的编辑，整轮修改进入单条可撤销历史记录。工作台已有明确标注“无真实模型”的固定计划演练侧栏；Agent 回归测试 27 项、既有图像与历史测试 91 项、严格 TypeScript 检查和 Vite 生产构建均通过。

**下一步先做 Electron 实际交互验收**：切换照片后验证目标绑定；运行明确用户指令；检查待确认建议在点击采纳前不改变参数；执行后撤销／重做并检查 sidecar 落盘。该轮通过后再确定首个 BYOM 多模态接口并进入真实模型接入。当前演练使用固定 EditPlan，不解析自然语言、不进行图像理解，也不代表 Agent 已接入模型。
